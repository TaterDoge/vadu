# NSH 架构

> 当前桌面翻译通过 Rust 内置 Chat Completions 适配访问服务商。第三方插件 VM 与授权桥为目标设计。实现进度见[迁移范围](../nsh-migration.md)。

## 1. 已确定的边界

- 保留用户安装第三方 JS 插件；内置与第三方插件遵循同一业务契约。
- 普通配置与平台能力优先使用 NSH 的 TS API；需要原生业务时才使用带类型的 Rust 模块，不建立 Electron 风格的 IPC、preload 或通用字符串 RPC。
- 授权、任务与插件宿主核心放在 Rust；厂商协议只在能力插件内实现，核心不内联 OpenAI 等厂商请求。
- 第三方 JS 在独立插件 VM 中执行，不装进 UI VM，不要求用户编译 Rust 动态库或 Wasm。
- 插件隔离与加载是 Vadu 要实现的能力，不是 NSH 已提供的翻译插件系统。

## 2. 窗口与运行时

NSH 自有窗口由同一个应用 engine 渲染，共享响应式状态与模块。设置主窗口和通过 `Window.open` 创建的翻译工作台，不等同于 Electron 的两个 renderer 进程。独立嵌入的 view 才可能拥有另一套 engine / VM。

主窗口通过 `src/tray.ts` 使用 `nsh/desktop` 的原生托盘，不新增 Rust 桥接。启动显示设置；关闭主窗口只隐藏，托盘可重新聚焦原窗口或退出应用，隐藏不卸载视图；生命周期配置见 [菜单栏托盘](../../README.md#菜单栏托盘)。

因此，两扇应用窗口可以共用视图状态，不需要互发窗口消息。普通配置统一由 TS 设置模块读取、校验和更新；UI 中的共享状态只是视图快照，不能绕过保存校验。

`App.tsx` 只挂载设置主窗口；TSX 窗口实现分别放在 `src/windows/settings/SettingsWindow.tsx` 与 `src/windows/translate/TranslateWindow.tsx`。设置窗口采用左右布局，侧栏是常驻 MenuItem 导航（Menu 本身是弹层，不作为侧栏容器），内容使用 `NavStack` / `NavPage`；五个一级分类用 `replace` 切换，不累积返回历史，选中态直接来自路由栈。

五个设置分类各自使用 `src/windows/settings/pages/<分类>/` 下的独立 Page 组件，路由配置通过 `render` 统一挂载当前页，不为快捷键页单独分支。`SettingsWindow.tsx` 负责侧栏、路由、滚动容器与内容区的可访问名称，不再渲染公共标题、分类说明或业务未迁移提示。快捷键页通过 TS Settings 校验、保存与重置组合键，通过 NSH keymap 临时录入；`src/shortcuts.ts` 集中声明已实现动作的 ID、作用域与执行函数，由 `setupShortcuts()` 统一观察已保存组合：全局作用域使用 NSH GlobalShortcut，窗口作用域通过响应式 `Window.get` / `state` 仅在目标窗口可见且聚焦时使用 NSH keymap。翻译窗组件不再读取快捷键配置或维护绑定；录入期间两类动作均暂停，管理器卸载时统一清理，重挂时可重新绑定仍打开的翻译窗；外观页提供显示模式、强调色与 Nova / Lyra 风格切换；服务商页管理翻译 Profile 与本地存储中的 API Key，通过原生模块查询模型。通用与备份恢复页为空容器。

主题由 `theme.json` 定义，`src/theme.ts` 用 NSH 的 `setTheme` / `setColorScheme` 更新应用级 token；两窗口共享主题及当前选择，不传窗口消息。字体随应用打包；现有容器、文字、图标与滚动条读取语义颜色 token，字号、行高、圆角与间距使用 NSH 内置类。当前外观偏好只存在运行期 signal，不读取或写入配置文件；重启恢复默认。外观尚未接入 Settings 持久化，不能将运行期切换视为已实现外观配置持久化。

翻译工作台定位为只通过快捷键唤起，不接入设置主窗口导航。当前 `openTranslateWindow()` 通过 `Window.open` 使用固定 ID `translate` 创建或重用翻译窗口，再聚焦；不设置父窗口。窗口类型与层级约束见[窗口与导航范围](../nsh-migration.md#2-窗口与导航范围)，不把翻译窗聚焦等同于激活整个应用。未固定的浮窗失焦时调用 `hide()` 并保留输入。固定后使用 `aboveDock` 层级，失焦时保持可见。设置窗口挂载时启动全局注册，隐藏不注销；配置更新后换绑，录入时暂停，卸载时注销且忽略过期回调。窗口切换与注册生命周期已有 headless 测试；跨应用真实按键、真实任务的关窗取消和发布构建生命周期仍需验证。

## 3. 职责与调用方向

现有调用从 UI 进入 Rust，由核心解析已保存的 Profile、读取匹配凭据，再调用 `src/plugins/openai.rs`。HTTP 层限制连接期限和重定向。下图描述后续的独立 JS 插件路径。

```text
设置中心 / 翻译工作台（NSH TSX，同一应用 engine）
    ├── 普通配置 → TS Settings → NSH Storage
    │ 按需使用带类型的原生调用 / 请求级回调
    ▼
Rust 应用核心（目标设计）
    ├── Profile、Secrets 与插件生命周期
    ├── 校验、任务表、取消、错误归一
    └── 插件宿主桥：受控 HTTP、凭据、日志
             ▲
             │ 调用上下文 / 结果
             ▼
独立 JS 插件 VM（按插件隔离，不共享 UI VM）
    └── 翻译 / OCR / TTS 的一次协议调用
             │ runtime.fetch，经宿主权限检查
             ▼
          外部服务
```

| 层          | 负责                                           | 不负责                                                |
| ----------- | ---------------------------------------------- | ----------------------------------------------------- |
| TSX 视图    | 输入、展示、页面草稿、按请求更新状态           | 厂商网络请求、直接读取 API Key 或写配置文件           |
| TS 设置模块 | 普通配置默认值、校验、串行读改写               | 密钥持久化、插件执行与授权                            |
| Rust 核心   | 受控能力授权、任务生命周期、插件管理、错误归一 | 厂商协议、插件内的提示词与响应解析                    |
| 插件        | 一次翻译 / OCR / TTS 调用与协议适配            | 自行读写配置、跨 Profile 取密钥、窗口、重试与缓存策略 |
| 平台设施    | 窗口、快捷键、NSH Storage、文件选择等          | 复用 Electron API 或绕过业务校验                      |

不预建缓存、自动重试、语言检测、术语表或万能能力调用框架。需要这些业务时，再在核心中设计；不由每个插件自行实现。

## 4. UI ↔ Rust：原生绑定，不是 IPC 复刻

项目保留 `#[native_module("vadu/native")]` 脚手架。普通配置与快捷键使用 NSH 已有 TS API，不增加 Rust 包装；确实需要原生业务时才沿用 `#[module]` / `#[class]` 与类型生成，生成的 `.nsh/types/vadu/native.d.ts` 不手工修改。

- 同步导出只做短小操作；网络与磁盘 I/O 异步执行，不能阻塞 engine。
- 一次性调用使用 Promise；翻译增量使用与开始请求一起登记的回调。
- 任务身份仍使用 `requestId`，用于并发、取消与过滤旧结果，不是 IPC 路由 ID。
- Rust 普通错误不保证保留自定义 JS 错误字段，业务失败必须显式传结构化错误。
- 不再建立 `vadu:<domain>:<action>` 通道表、`window.vadu`、preload 或窗口广播层。
- NSH 的 `host.call` 面向嵌入宿主通信；本 mixed Rust 工程不为业务再包一层无类型 RPC。

输入、事件、取消和错误语义统一见[原生 API](./native-api.md)。不要在架构文档里再维护一份通道表。

## 5. 插件宿主与信任边界

独立插件 VM 由 Rust 宿主管理，只注入当前调用需要的能力。UI 模块、原生模块注册表和系统模块不得直接暴露给插件。

- 网络只能通过宿主受控桥；凭据只向本次调用所属 Profile 提供。
- 设置内存上限、执行期限与中断机制；不能依赖插件主动检查取消来处理死循环。
- 插件加载失败、崩溃或超限，应终止所属任务并标记插件不可用，不能阻塞设置窗口启动。
- 禁用、卸载与应用退出要终止相关任务并释放 VM。
- 安装前展示来源与权限，用户确认后才启用；权限扩大需再次确认。

这是待实现的隔离目标，不是现有安全保证。QuickJS VM 隔离也不等于 OS 进程沙箱；原生桥和运行时漏洞仍影响宿主安全。未经隔离验证，不应对外开放第三方安装入口。

NSH 发布模式禁用 UI 中的 `eval` / `new Function` 等动态执行。不能用 UI 动态求值装插件，也不能通过关闭发布加固来绕过。独立插件 VM 的模块加载器须单独实现并验证发布构建。NSH 的签名 `.nsh` 应用包不等同于 Vadu 的业务插件包。

插件格式、调用上下文、权限与 AI 协议适配见[插件规范](./plugin-spec.md)。

## 6. 数据与保密

| 概念     | 唯一职责                                                         |
| -------- | ---------------------------------------------------------------- |
| Plugin   | 一种能力的实现、配置 schema 与权限声明                           |
| Profile  | 用户配置实例，绑定一个插件；包含端点、模型等非密钥配置与启停状态 |
| Preset   | 创建 Profile 的只读模板；更新模板不得覆盖用户已有实例            |
| Settings | 应用级偏好，不混入某个服务商配置                                 |
| Secrets  | 按 Profile 隔离的 NSH Storage 键，不混入普通配置                 |

核心解析明确选中的 Profile，再决定插件；不得暗取第一个 AI 配置。Profile 关闭后保留数据，但不再接受新任务。不存在或插件不可用的引用要报错，不能静默换厂商。

普通配置由 `src/settings.ts` 在同一应用 engine 内串行读取最新文档并修改单项，通过 NSH Storage 的 `vadu.config` 整包保存，底层后台写入并原子替换。此队列不提供跨进程事务。当前保存快捷键与服务商 Profile。保存服务商时，普通配置先写入 `vadu.config`，本次输入的密钥再写入独立键 `vadu.secret.<profileId>`。NSH 0.6.0 的写盘回执、删除顺序和整包备份恢复方案见[配置存储设计](./storage.md)。

设置页默认只查询 API Key 状态，用户可按需临时查看当前服务商的已保存密钥。新输入的密钥只短暂存在于输入与提交路径，提交后清空。密钥是 NSH Storage 中的明文；读取失败时不覆盖原数据。凭据和授权的细节见[原生 API](./native-api.md#6-输入凭据与授权)。

日志默认不记录密钥、Authorization 头、翻译原文、译文或上游响应正文。确需识别密钥时最多前 4 后 4 位，短密钥全部遮蔽；正常诊断只记 `requestId`、插件 ID、耗时与安全错误码。

卸载插件不得静默删除关联 Profile 或密钥；删除配置、凭据或恢复覆盖必须单独确认。整包备份格式与确认后恢复流程已有设计但尚未实现；Electron 数据导入另行确认，不承诺旧格式兼容，也不继承旧版明文密钥导出行为。

## 7. 框架能力与待验证项

| 已核对的 NSH 机制                     | Vadu 仍需验证 / 实现                                                   |
| ------------------------------------- | ---------------------------------------------------------------------- |
| 应用自有窗口共享 engine               | 局内按键与置顶层级的跨平台原生验证、真实任务关窗取消与发布构建生命周期 |
| Rust 导出生成 TS 类型，支持异步和回调 | 业务 DTO 的生成、回调存活与任务清理                                    |
| JS fetch 有流与 AbortController       | 插件 VM 中的受控流式 HTTP 桥、真实上游取消                             |
| NSH 0.6 的 Rust `fetch` 缓冲完整响应  | 内置适配使用 Rust 流式 HTTP 客户端限制响应体积，并在取消时释放上游连接 |
| 能力声明可限制 NSH 提供的服务         | 每插件权限、URL / 重定向校验；Rust 原生代码不会自动受该声明约束        |
| NSH 使用 QuickJS 与有限标准模块       | 独立插件 VM、模块加载、资源配额与 npm 包兼容                           |

当前 `nsh.json` 没有声明 capabilities，不能称应用已处于最小权限沙箱。实现时应按实际使用收紧；应用级声明不能替代每插件、每 Profile 的授权。
